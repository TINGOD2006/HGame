> 對應決策：Unity 6000.3.10f1、Ink 對話、高解析動漫風、一人開發、雙軸並存。
> 目的：在寫第一行程式前，把「誰負責什麼、資料怎麼流、哪裡會痛」講清楚。

## 1. 分層原則

```
┌─────────────────────────────────────────────┐
│  Presentation（Unity）                       │
│  Scenes / MonoBehaviour / uGUI / Animator    │
│  TownController、BattleController、Views      │
├─────────────────────────────────────────────┤
│  Application（Unity 層，薄）                  │
│  EventRunner、DialogueService、SaveSystem、   │
│  SceneLoader、AudioService                   │
├─────────────────────────────────────────────┤
│  Domain（純 C#，不引用 UnityEngine）          │
│  GameContext、BattleModel、DamageCalculator、 │
│  DungeonGraph、RelationshipService、          │
│  EventAvailabilityService、SaveData           │
└─────────────────────────────────────────────┘
```

**為什麼要分**：一人開發最怕「改了平衡要開 Unity 跑 3 分鐘才驗證」。Domain 層用 EditMode Test 毫秒級驗證，Presentation 層只負責「把狀態畫出來」。這是 10 週能收尾的關鍵，不是為了漂亮。

**Assembly Definition**：
- `Game.Core`（Domain，無 Unity 依賴）
- `Game.Unity`（MonoBehaviour 與 UI，引用 Game.Core）
- `Game.Editor`（資料驗證工具）
- `Game.Tests`（EditMode 測試）

## 2. Domain 層類別職責

| 類別 | 職責 | 關鍵方法 |
|---|---|---|
| `GameContext` | 全局可變狀態容器（日、章、旗標、女主角、玩家、背包、已解鎖 CG） | `AdvanceDay()`、`GetHeroine(id)` |
| `HeroineState` | 單一女主角的 trust / desire / seenEvents | `AddTrust(n)`、`AddDesire(n)` |
| `GameFlags` | 具名旗標集合；序列化成字串陣列（不用 bitmask，方便除錯） | `Set(name)`、`Has(name)` |
| `RelationshipService` | 雙軸規則、四象限判定、章末結算 | `Quadrant(id)` |
| `EventAvailabilityService` | 依條件掃出「現在可播」的事件，依優先級排序 | `GetAvailable(context)` |
| `BattleModel` | 純資料的戰鬥狀態機：回合、行動、勝負 | `Step(action)`、`IsOver` |
| `DamageCalculator` | 傷害公式（靜態、可測） | `Compute(attacker, defender, skill, rng)` |
| `DungeonGraph` | 節點圖生成與連線 | `Generate(floorConfig, seed)` |
| `SaveData` / `SaveMigrator` | 存檔 POCO 與版本遷移 | `Migrate(json)` |

**規則**：Domain 不碰 `GameObject`、`Sprite`、`Coroutine`、`Time.deltaTime`。需要隨機就傳 `IRng` 進去。

## 3. Unity 層職責

| 類別 | 職責 | 備註 |
|---|---|---|
| `GameBootstrap` | Boot 場景初始化、建立 GameContext、載入設定與存檔 | 唯一 DontDestroyOnLoad 的入口 |
| `SceneLoader` | 非同步切場景＋淡入淡出＋Loading 提示 | 避免切場景時卡頓 |
| `EventRunner` | 事件流程總管：條件 → 演出 → 對話 → 效果 → 標記已看 | 核心，先寫好 |
| `DialogueService` | 包裝 Ink Story、註冊 external 函式、逐行播放 | 見第 4 節 |
| `SaveSystem` | 槽位管理、原子寫入、自動存檔 | 見第 6 節 |
| `TownController` | 據點日夜循環、設施互動 | 呼叫 EventRunner |
| `DungeonController` | 節點地圖 UI、移動、探索度、撤退 | |
| `BattleController` | 驅動 BattleModel、播放動畫、回報結果 | 單向：Controller → Model → 事件 → View |
| `AudioService` | BGM/SE 播放與淡入淡出 | 全域 |

**UI 原則**：每個 Scene 一個 Canvas；UI 元件只讀狀態、發事件，不直接改 Domain。用 C# `event` 或簡單 callback，不引入 DI 框架。

## 4. 事件與 Ink 的邊界

**分工**：JSON 管「什麼時候播、演出什麼、給什麼獎勵」；Ink 管「台詞與選項」。

```
events/s1_night.json  ──┐
                        ├─→ EventRunner ─→ DialogueService ─→ Ink story
Ink/s1_night.ink        ─┘        │
                                  └─→ 演出（BG / CG / 立繪 / BGM）→ 效果寫回 GameContext
```

- Ink 只透過 **external function** 讀寫 Domain，不直接碰存檔：
  - `getTrust(id)`、`getDesire(id)`
  - `addTrust(id, n)`、`addDesire(id, n)`
  - `hasFlag(name)`、`setFlag(name)`
  - `giveItem(id, n)`
- 演出指令（換背景、播 CG、換表情）由 **JSON 的 presentation 欄位**驅動，不寫進 Ink。這樣全年齡／成人版只需換 JSON 與素材。
- **Ink state 不存檔**：MVP 的事件是「進場 → 對話 → 結束」，中途不離開；選項造成的數值變化立刻寫回 GameContext。若之後需要「對話中途存檔」，再開 `story.state.ToJson()`。

## 5. 典型流程（時序）

**A. 一天結束 → 觸發夜間事件**

```
DayCycleController.EndDay()
  → GameContext.AdvanceDay()
  → EventAvailabilityService.GetAvailable(context)   // 條件過濾＋優先級排序
  → EventRunner.Play(event)
       → 載入 presentation（BG/CG/立繪）
       → DialogueService.Play(inkPath)
            ↔ Ink externals 讀寫 GameContext
       → 套用 effects（gold/item/flag/seenEvents）
       → 記錄解鎖 CG
  → SaveSystem.AutoSave()
```

**B. 迷宮 → 戰鬥 → 回城**

```
DungeonController.EnterNode(battle)
  → SceneLoader.Load(Battle)（帶入 enemyId 與戰鬥種子）
  → BattleController 初始化 BattleModel
  → 回合循環（玩家行動 / 敵方行動）→ 勝負
  → 戰鬥結果寫入 GameContext（HP、掉落、探索度）
  → SceneLoader.Load(Dungeon)（還原節點位置）
```

## 6. 存檔

- 序列化：**Newtonsoft Json**（`com.unity.nuget.newtonsoft-json`）。理由：字典、多型、欄位增減都比 `JsonUtility` 好處理。
- 路徑：`Application.persistentDataPath/saves/slot_1.json`、`auto.json`。
- **原子寫入**：先寫 `slot_1.json.tmp` → `File.Replace`，避免斷電壞檔。
- 版本：`"version": 1`，`SaveMigrator` 依版本補欄位。
- 存檔時機：日結束、從迷宮回城、手動存檔、事件播放完畢。
- **MVP 不做雲端存檔**。

## 7. 資料驗證工具（一人開發的效率關鍵）

`Game.Editor/DataValidator`：選單一鍵檢查

- 事件 JSON 的 `id` 是否唯一、`inkPath` 是否存在
- 條件引用的 flag 是否在某處被 `setFlag`（避免永遠不觸發的事件）
- `presentation.cg` 是否在解鎖清單中、素材是否存在
- 敵人／道具引用是否存在
- 事件可達性簡查（以章節進度模擬）

**沒有這個工具，後期 30 個事件出現「永遠不觸發」的 bug 會查一整天。**

## 8. 測試策略

| 層級 | 測什麼 | 工具 |
|---|---|---|
| EditMode | 傷害公式、四象限、事件條件、存檔遷移、節點生成 | Unity Test Runner |
| PlayMode | Boot → MainMenu → Town → Dungeon → Battle → 回城 煙霧測試 | Unity Test Runner |
| 手動 | 每日循環、事件跳過、回想重播 | 試玩清單 |

**原則**：Domain 的每個公式至少有 1 個測試；不追求覆蓋率，追求「改數值不會炸」。

## 9. 關鍵取捨（已建議，待確認）

| 項目 | 建議 | 替代方案 | 代價 |
|---|---|---|---|
| 分層 | Domain 純 C# ＋ Unity 層薄 | 全部 MonoBehaviour | 快 2–3 天，但後期難測、難改 |
| 事件粒度 | 一事件一 Ink，不存 Ink state | 一章一 master story | 存檔粒度粗，但複雜度低很多 |
| 序列化 | Newtonsoft | JsonUtility | JsonUtility 免費但字典難處理 |
| 驗證工具 | W1 末花半天做 | W4 後再做 | 晚做＝多花 1–2 天抓 bug |

## 10. 已知風險

1. **Ink 學習曲線**：若卡住超過 2 天，立刻切回「自製 JSON Runner」，不要硬撐。
2. **EventRunner 變成上帝類別**：它只負責「串流程」，規則留在 Domain，超過 300 行就拆。
3. **AI 素材匯入規格不一致**：先定好 PPU、解析度、命名規則，用 `AssetImportPresetter` 統一。
4. **場景切換導致狀態遺失**：所有跨場景狀態只放 GameContext，Scene 內的東西一律可重建。
